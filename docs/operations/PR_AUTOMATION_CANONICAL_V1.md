## 5. Measurements, truthfulness and root-cause decisions

For each comparable PR cohort calculate where source events actually exist:

`created → first CI queued → first CI started → first causal failure → repair_started → final mandatory PASS (current HEAD) → protected MERGED → served deployment → HH_FUNCTIONAL_SMOKE_V1`.

Report **n, coverage, mean, p50, p95, sample interval, source URLs, UTC timestamps** for each stage (24h and 14d only where cohort evidence exists). Track independently:
- **Error → Repair:** first confirmed causal error → actual repair start, not triage/dispatch.
- **CI First Pass:** PRs passing their *first complete required-check wave on the same head* / eligible PRs, with both counts.
- **Green → Merge:** final applicable exact-head mandatory PASS → actual `merged_at`; check review and lease.
- **Merge → functional LIVE:** linked merge SHA → actual first observed feature smoke after deployment, with ancestry and alias. Report upper-bound observation intervals honestly.

Use `PENDING` for active jobs, `FAILED` only for terminal causal errors, `CANCELLED` for superseded/terminated jobs, `UNKNOWN` for missing history, `N/A` where a stage is not applicable. Historical HEAD success or failure = `STALE`. Do not treat a 0-size verified sample as "0 minutes". Runner-minutes != workflow wall time; queue delay != execution time. Failed Specialist dependency handling must distinguish pending/running/failed/cancelled without blind retries.

Each `HH_OPT_ACTION` uses a stable root ID, priority, exact current evidence/HEAD, acceptance test and owner, with `READY/IN_PR/VERIFY/HOLD/DONE` state. :20 issues **at most three** next actions, ranked by measured recoverable latency and number of actually affected PRs. Repair workers verify before executing.

**2026-11-14 · Specialist/AutoMerge production-base parity:** The event-driven AutoMerge freshness check uses `lib/ci/production-base-impact.mjs` from the same SHA-pinned protected production checkout as its route classifier. For a verified, otherwise green exact-HEAD Core/Specialist run, it may retain the tested HEAD on a bounded descendant BASE only when that immutable Specialist policy proves a disjoint, non-runtime documentation-only or narrowly allowlisted CI-maintenance advance (plus the existing independently verified public raster exception). Unknown paths, run/check provenance, overlap, conflict, auth/consent/privacy/payment/CI policy, missing evidence or altered HEAD still block. Incompatible but ancestry-proven BASE changes are routed through the existing one-shot protected revalidation, not passed or globally rerun. Every reused sensitive BASE SHA is pinned again before ARM; no extra workflow or poller. LIVE website code remains a separate production-deployment concern.

## 5.1 CI wave suppression — prepare before PR; one published HEAD (2026-11-04)

**Root-cause evidence:** [ten-PR stage audit](PR_LAST_TEN_STAGE_AUDIT_20261104.md). PR #3502 had 17 commits, of which 10 were published after it opened; its production branch received 11 distinct Core CI waves. PR #3509 had 8 commits and 4 Core waves, including two first-attempt runs associated with one identical SHA. The existing production Core workflow triggers on `opened`, `synchronize`, `ready_for_review` **and `edited`**. The existing per-PR concurrency rule cancels superseded work, but **cannot prevent a wave from being created**. GitHub wave counts are NOT proof of billing.

**Mandatory source-publication contract for :35 Repair Product, :40 Optimizer Fixes, :45 Conflict Repair and any PR-authoring Chat agent:**

**ONE VERIFIED ROOT → ONE PR — mandatory BEFORE ANY REMOTE BRANCH WRITE.** Every :35 Repair Product, :40 Optimizer Fixes, :45 Conflict Repair and other code/PR author must check the existing signed issue/root/HH_OPT_ACTION, current owner lease and one bounded set of OPEN PRs targeting the correct base plus directly linked superseded/merged candidates. If a current PR already addresses the **same proven defect and fix**, REUSE_OR_HANDOFF_EXISTING_PR instead of creating a second. If the fix is MERGED and verified included on the actual target branch, ALREADY_RESOLVED; do not publish. Same files/title without proven shared root is only a hint: decide INDEPENDENT_SCOPE with evidence or HOLD_DUPLICATE_UNVERIFIED. If the inventory, base or owner is unknown, HOLD_INCOMPLETE_INVENTORY / HANDOFF_OWNER; never infer status, cancel unrelated work or repeat Core. [Bounded decision tree](PR_REMOTE_ONE_PUBLISH_V1.md#one-root--one-pr-duplicate-admission-before-any-remote-write). An extra PR can create costly Core/preview waves even when later closed unmerged; avoid it before opening rather than adding another workflow.


**CRITICAL: the first REMOTE push is the CI/deployment boundary, not merely PR opening.** A GitHub `push` can trigger Actions, a Vercel/Netlify/Cloudflare preview, or other metered automation even with no PR. Before the first branch ref update, check this repository's currently effective `push` and PR triggers, deploymentEnabled/hosting integration and quota exposure. Prepare and test the entire change locally/in memory; on GitHub Connector use **blobs → one tree → one commit → one leased ref update**, then open the PR. A newly created empty ref is not a substitute for checking external `create` hooks. If no safe no-extra-cost path can be established, `HOLD_COST_UNVERIFIED` instead of intermediate remote commits. See [atomic pre-publication runbook](PR_REMOTE_ONE_PUBLISH_V1.md).

1. **STAGE BEFORE OPEN.** Prepare all coherent source, tests, workflow and documentation edits on a **branch that has no open PR**. Run relevant available syntax/unit/route checks *before* creating the PR. For tools that produce one commit per file, finish these operations while the PR is still unopened; preferably publish a validated multi-file Git tree in **one branch-ref update** (one source HEAD change). Do not run a heavy production CI/deploy simply to test an incomplete patch. Never defer required checks after publishing.
2. **PUBLISH ONCE.** Open one thematic PR only after a coherent patch and tests are ready. Prefer **one initial required Core wave** on a complete source revision, not a PR created after the first half-written file. If work is still incomplete, continue preparing the unopened branch. Draft is not a zero-work guarantee: `synchronize` still creates a workflow record, and optional workflows may run; it is not the preferred batching method.
3. **FREEZE WHILE VALIDATING.** After opening the PR, if required exact-HEAD Core/Guard/Specialist checks are queued or running, do **not** publish incidental commits, no-op commits, formatting/doc-only follow-ups, discretionary base refreshes or duplicate bot edits to PR title/body. GitHub `pull_request.edited` is a real Core trigger even when the SHA is unchanged. Use a PR comment, issue ledger or existing Google Doc for progress instead of PR-body rewrites. Do not disable `edited` blindly: existing metadata-only missing-Core recovery may depend on it.
4. **ONE EVIDENCE-BASED REPAIR BATCH.** When a required current-HEAD check fails with a verified root cause, the responsible owner may produce a locally validated, complete repair in **one source publish**, updating the lease and preserving original safety assertions. A new HEAD is then correctly rechecked by Core. If multiple failures are identified, collect them before this single corrective push; a further wave is justified only by a *new verified failure* or essential security/correctness issue. Urgent confirmed P0/security regressions may interrupt a running wave, but never merge untested final HEAD.
5. **DO NOT GENERATE FALSE CI WAKEUPS.** No independent `workflow_dispatch`, manual rerun, empty source commit, branch update or metadata `edited` solely to get a new green status when a valid exact-HEAD required run is queued/running/successful. The pre-existing `ci-pr-ci-worker` one-shot fallback is allowed **only** for a confirmed PR with **zero** Core PR-run history and its existing strict owner lease. A genuine failed same-HEAD run requires root-cause repair or explicitly verified transient retry policy; never suppress mandatory checks.
6. **MEASURE, DO NOT HARD-BLOCK.** :20 Optimizer Analysis uses its **existing bounded GitHub run/PR snapshot**, not new polling, to report for completed comparable PRs: first Core enqueue delay, **distinct source-HEAD Core waves**, same-HEAD duplicate waves (same source SHA and distinct first-attempt run IDs), post-opening source updates, cancelled run count, first-pass success, and created→merged / Green→Merge clocks. Report `n`, full/partial history and exact run links; no claim that the time between commits is all wasted CI time. **Operating target:** normally 1 initial wave, at most 1 verified repair wave; 3+ waves is a diagnostic alert for analysis, **not** an excuse to bypass checks or freeze a necessary fix. Separate legitimate repairs from avoidable intermediate publishing. The existing Core archive additionally distinguishes `new_head_after_success_count/ms` (HEAD change following successful previous Core) from `after_failed_count/ms`; this is a *review signal*, never proof a commit was needless, because Specialist/Guard/merge gate may still be pending or failing. :20 must consult linked exact-HEAD run-pair evidence and route any `HH_OPT_ACTION` to the single PR owner; do not reset a green CI wave merely because this counter rose.

**Tooling for atomic publication:** When connector edits to multiple files are needed, create blobs/tree/commit on a prepared branch and advance it once with current-HEAD compare-and-swap; never force-push or overwrite a concurrently changed branch. This is the same repository and existing GitHub API, not a new service. **Do not** create multiple remote commits even on an unopened branch when push-triggered preview/CI is possible; PR opening is **not** the first admission boundary. If an atomic Git-object update is unavailable, stage a complete local worktree and push it once (or `HOLD_COST_UNVERIFIED` if the remote side effects cannot be bounded). Never force push or overwrite another writer. Cite [PR_REMOTE_ONE_PUBLISH_V1](PR_REMOTE_ONE_PUBLISH_V1.md) for exact GitHub connector steps. Do not create separate PRs for pieces of one verified change solely to hide wave counts.

**Acceptance/financial guard:** No change to existing Core, Specialist, Guard, workflow triggers, branch protection, merges, schedules, runners, token scopes or Vercel deployments. The policy itself adds no CI runs and no recurring API workload. Effective reduction is verified only against subsequent published PRs, not claimed merely because this text merged.
