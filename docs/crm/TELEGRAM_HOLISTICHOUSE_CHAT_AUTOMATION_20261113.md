## Continued Business conversation and confirmed CRM enquiry (13 Nov)

The existing signed Telegram Business webhook now implements a bounded three-step flow: localized service draft → online/in-person/written format → explicit typed Confirm. Only after Confirm does the server record a single encrypted enquiry in existing `app.public_service_enquiries`, with a fixed service/locale/format, signed-provider consent HMAC, no raw Telegram chat ID or health text. It returns the HH reference and never claims booking or payment. Free text is not stored or forwarded to an AI.

A private `app_private.crm_tg_business_service_sessions` RLS/FORCE RLS table stores only HMAC pseudonyms and service state; signed inbound `hh_app_inbox` can modify it, while backend can read only a scoped confirmed operation for at most 15 minutes. A shared advisory lock prevents STOP and submission racing. Explicit Cancel discards a pending order; STOP is terminal. Unknown personal messages are ignored; the account owner continues substantive communication in @holistichouse. This is an owner-visible CRM service request, **not** a provider-linked two-way CRM messenger thread or a paid appointment.

The new code has two release gates: additive private database migration and `HH_CRM_TG_CHAT_AUTOMATION_ENABLED=true` AFTER owner attaches @holistichouse_bot in Telegram Chat Automation with can_reply, then actual second-account E2E and STOP verification. The public Request → Telegram draft remains working independently while disabled. No new bot, API fees, external LLM, paid option or schedule.

## Warm service-specific dialogue and atomic CRM completion

A recognized, customer-authored [HH-REQ] message now receives one short, contextual "I see you're interested in…" acknowledgement in RU/EN/ES, not a generic free-review AI interview. The bot asks only for a format (online, in person, written), then explicitly asks to type Confirm or Cancel. Bounded natural variations such as "мне удобнее онлайн" choose only the format; "да/yes" and arbitrary text never constitute submission consent. No appointment, price or payment is invented.

The existing private table uses FORCE RLS: hh_app_backend gets only a column-scoped UPDATE with an exact operation ID, fresh consent and transition-only policy (committing → submitted). An enquiry INSERT and session submission now share one backend transaction and one advisory lock also used by the signed inbox STOP/Cancel. A STOP/Cancel that wins the lock prevents the INSERT; if the INSERT wins, the request was already submitted and STOP only prevents further automatic contact. Duplicate Confirm reuses the operation and reference. The server admits up to four bounded terminal receipt/STOP messages per chat per day, separate from the three normal conversation replies; the existing global cap, HMAC and signed Telegram checks remain.

Deployment still requires protected merge and current-head Core/Specialist/Guard, private migration application and RLS verification, owner Telegram Business rights and second-account physical end-to-end proof. The production flag remains OFF until those checks; this PR does not enable paid providers, AI data processing for Business orders, new schedules or marketing.
