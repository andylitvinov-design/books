# Holistic House CRM — программа развития v5.1

**20 октября 2026 · America/Toronto**  
Источник требований: [CRM #985](https://github.com/andylitvinov-design/books/issues/985) и [Google Docs — план и ТЗ](https://docs.google.com/document/d/1cuW1vaQrxUECQWk9b5kDvO1fRcHnbalTDOq8BppZZT8/edit). Основная ветка: `codex/public-book-library`.

## Результат для мастера

Мастер открывает «Моя практика → Клиенты», видит новые сообщения и задачи на сегодня, выбирает следующее действие и сразу попадает в соответствующую заявку. После ответа, отметки просмотра или изменения задачи данные обновляются. Новое сообщение, необходимость ответа и просроченная задача остаются разными признаками.

PR #1244 уже влит: он добавил новые сообщения и явные отметки просмотра. Продолжение v5 (#1303/#1312/#1317) добавило задачи мастера и добровольные Web Push. Этот документ описывает следующую доработку и критерии следующих этапов. Датированные записи о выпуске сохраняются в #985; наличие кода и реальную проверку доставки следует отмечать отдельно.

## Модуль 1. Ежедневная рабочая очередь — v5.1

| Возможность | Поведение | Проверка результата |
|---|---|---|
| Новые сообщения | Только клиенты с сохранёнными сообщениями, ещё не отмеченными просмотренными | Клиент может исчезнуть из «Новые», но остаться в «Ждут моего ответа» |
| Ждут моего ответа | Последняя общая реплика пришла от клиента либо новая заявка ещё не обработана | Внутренняя заметка мастера не снимает необходимость ответа |
| На сегодня | Клиенты с открытой задачей на текущую дату Toronto | Завершённая задача не попадает в фильтр |
| Просрочено | Клиенты с открытой задачей раньше текущей даты Toronto | Задача на сегодня не считается просроченной |
| С задачами | Клиенты с любой открытой задачей по принадлежащей мастеру заявке | Фильтр работает и для задач за пределами первых 150 подробных записей |
| Ближайшие действия | Первые пять открытых задач по сроку; имя клиента, тип действия, дата | Из очереди раскрывается именно нужная заявка и задача, включая старую заявку того же клиента |
| Доступность | EN/RU/ES; перенос длинных подписей; элементы управления от 44 px | Фокус клавиатуры переходит к выбранной задаче; учитывается reduced motion |

**Полные счётчики:** API возвращает `practitionerTaskSummary` с датой Toronto и агрегатами по всем доступным заявкам мастера. Подробная очередь остаётся ограниченной 150 строками. Это сохраняет небольшой ответ и не превращает ограничение очереди в неверный общий счётчик. UI дополнительно исключает неподтверждённые публичные заявки и чужие идентификаторы из задач.

Если кабинет оставался открытым до следующего дня, при возвращении на экран выполняется одно обновление за день, без фонового опроса. До успешного обновления явно указана дата сохранённых показателей; доступна ручная повторная попытка.

## Модуль 2. Надёжная переписка — v5.1

1. Порядок сообщений сохраняет микросекунды PostgreSQL. UUID используется только при одинаковом времени. Отметка просмотра выбирает самое позднее фактически загруженное общее сообщение другого участника.
2. Более старый HTTP-ответ не может восстановить старое количество новых сообщений или старое разрешение отвечать после обновления. Запросы привязаны к конкретной учётной записи и заявке; закрытие диалога отменяет ожидающие ответы.
3. Подгрузка ранних сообщений сохраняет курсор. Если между обновлениями пришло больше одной страницы, новый курсор позволяет последовательно прочитать пропущенный промежуток.
4. Допускается ограниченный JSON-запрос до 8192 байт. Существующие ограничения текста сохраняются: ответ — 1200 символов JavaScript, приватная заметка — 800. Поэтому полный разрешённый ответ на русском проходит проверку размера запроса.
5. Отправка блокирует точную строку заявки через `FOR UPDATE OF r` перед проверкой дубля и суточного лимита. Две вкладки не могут одновременно занять последнее свободное место. Повтор с тем же operation ID сохраняет одну запись и не инициирует повторное уведомление.

Изменения используют существующую авторизацию, шифрование и RLS. Новых таблиц и миграций для v5.1 не требуется. Фильтры и выбор задачи не отправляют сообщения и не отмечают переписку просмотренной.

## Проверка v5.1

Основной автоматический gate — `.github/workflows/hh-crm-source-check.yml`. В него включены:

- `tests/practitioner-client-work-queue.test.mjs`: независимость фильтров, проверка принадлежности задач, переход к старой заявке, полные агрегаты вне ограниченной очереди, совместимость с прежним ответом API.
- `tests/practitioner-conversation-state.test.mjs`: микросекунды и часовые пояса, исключение своих сообщений и заметок из просмотра, объединение страниц, пропущенные промежутки, запоздавшие ответы и смена аккаунта.
- `tests/practitioner-message-send.test.mjs`: реальные функции чтения тела, проверки текста, шифрования и отправки с изолированной моделью транзакций; русский/английский/испанский и другие Unicode-строки, превышение размера, параллельная отправка и повтор при достигнутом лимите.

Для последнего файла необходим серверный режим Node:

```sh
node --conditions=react-server --test tests/practitioner-message-send.test.mjs
```

Дополнительно выполняются существующие проверки CRM/контактов/согласий/уведомлений, проверка синтаксиса JSX и production-сборка Next.js. Моделирование конкурентной базы подтверждает поведение функции, но не заменяет тест реальных сессий и RLS.

## Модуль 3. Приёмка на настоящих аккаунтах

| Сценарий | Ожидаемый результат | Свидетельство завершения |
|---|---|---|
| Клиент → назначенный мастер | Созданная заявка и сообщения видны обоим в их кабинетах | Проверка двух подтверждённых тестовых аккаунтов |
| Другой мастер | Чужие сообщения, заметки и задачи не выдаются | Запросы дают 403/404 без данных |
| Новое / просмотрено / нужен ответ | После явной отметки «Новые» уменьшается; «Ждут ответа» сохраняется до ответа | Проверка интерфейса обеих сторон |
| Задача | Создание → перенос → выполнение → повторное открытие | После перезагрузки состояние сохраняется |
| Web Push | Добровольно подписавшийся получатель видит нейтральное уведомление; ссылка открывает нужную заявку после входа | Фактическое получение на телефоне |
| Мобильный интерфейс | Основные действия доступны на 360, 390 и 430 px, длинные EN/RU/ES подписи не перекрываются | Визуальная и клавиатурная проверка с синтетическими данными |

До такой приёмки нельзя объявлять подтверждёнными реальную доставку на устройство, полноценный двухаккаунтный E2E или тест VoiceOver/Safari. Не нужно создавать настоящие сообщения клиентам ради технической проверки.

## Модуль 4. Внешние каналы

Порядок остаётся прежним: Telegram пилот → WhatsApp → Instagram/Facebook. Каждый канал принимается отдельно: собственные официальные реквизиты → подтверждённый получатель и согласие → входящий webhook → сохранение диалога → ручной ответ → реальный статус провайдера → отказ от сообщений.

Ключи, согласия и расходы не возникают из факта слияния PR. Готовность адаптера и подтверждённую доставку следует показывать как отдельные состояния. Текущая доработка не активирует внешние каналы и не меняет рабочий webhook Telegram.

Курсовые Lead 1/Lead 2 проверяются отдельным сценарием: начало курса и запрос личной инициации создают связанные события без дублей; содержание личного письма и отзывов остаётся в защищённом разделе курса.

## Модуль 5. Масштабирование и делегирование

| Следующая работа | Что реализовать | Критерий завершения |
|---|---|---|
| История выполненных задач | Постраничная выдача после текущих 80 записей по заявке | Старую завершённую задачу можно найти и открыть без снятия серверных ограничений |
| Публичные обращения | Продолжение списка после текущих 250 записей | Нет скрытой потери старых обращений; пагинация остаётся в границах одного мастера |
| Рост каталога клиентов | Постраничная выдача заявок и независимые общие показатели | Список не загружает всю историю при каждом открытии |
| Помощник мастера | Назначение конкретных заявок, ограниченные действия, отзыв доступа, аудит | Помощник видит только явно предоставленные заявки; доступ немедленно отзывается |
| Срок хранения | Согласовать правила хранения/удаления рабочих сообщений и журналов | Реализация соответствует утверждённым правилам, имеет проверяемый сценарий удаления |
| Показатели работы | Число новых запросов, запросов без ответа, задач на сегодня/просроченных и завершённых | Показатели вычисляются из сохранённых событий, без догадок о внешних доставках |

Эти работы не следует выдавать за завершённые в v5.1. Для делегирования сначала нужен отдельный проект прав доступа; глобальный статус «мастер» не даёт доступ ко всем клиентам.

## Простая инструкция мастеру

1. Откройте [Моя практика → Клиенты](https://holistichouse.vercel.app/ru/app/practice?panel=clients).
2. Начните с «Новые сообщения», затем проверьте «Ждут моего ответа».
3. Отметьте прочитанные сообщения кнопкой внутри открытой переписки. При необходимости сохраните ответ.
4. Откройте «На сегодня» или «Просрочено». Нажмите задачу в «Ближайшие действия», чтобы перейти к её заявке.
5. Завершите задачу либо перенесите дату; используйте «Обновить клиентов», если данные менялись в другой вкладке.

Откат: вернуть commit этой доработки через обычный PR или восстановить предыдущий проверенный deployment. Схема данных не менялась. При откате полный подсчёт задач снова ограничивается прежним интерфейсом; возвращаются и исправленные здесь ограничения переписки.
