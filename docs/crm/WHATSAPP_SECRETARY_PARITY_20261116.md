# Holistic House WhatsApp service intake + shared Secretary (2026-11-16)

## Scope
The existing Meta-signed WhatsApp webhook and private CRM are the only transport and store. This does not create a second bot, model, provider, database, timer, paid template, or authentication method.

### Behaviour once official Meta number is connected
- Five exact published service names in the existing website WhatsApp draft include a public `[HH-REQ:service:locale]` marker; nothing is transmitted until the visitor presses Send in WhatsApp. No medical, account, or client material enters this marker.
- On a correctly signed, fresh WhatsApp message from the configured business phone, the existing encrypted CRM consent workflow now stores the selected service and format in its FORCE-RLS session. The short branch asks: explicit CRM/reply consent → preferred format → one question about the goal. Only consented answers enter the CRM Messages contact/thread. STOP remains terminal. After this signed, consented step, a guarded backend transaction creates a single idempotent `public_service_enquiries` lead and HH reference; it is not a paid booking.
- If a visitor asks an explicit public product, course, price, or material question outside any active private intake, the optional secretary reuses the same source-verified published catalogue as Telegram. It provides first-party URLs as WhatsApp text, without passing customer content to another AI model. No unsolicited sales.
- Generic free express review still uses its full approved six-stage WhatsApp diagnostic. An active consent/question stage always takes priority over catalogue FAQ.

## Explicit limits
- A GitHub merge is not proof of a connected WABA or customer delivery. As of this implementation, the connected WhatsApp account/Meta credentials and physical sender are not proven.
- The service branch creates the encrypted CRM contact/thread, an idempotent public-service enquiry, and a durable owner-notice intent. Actual @Andydotbot delivery remains gated by verified owner pairing and Telegram Bot API acceptance; no appointment or payment is implied.
- Do not forward medical records or special-category health data into an AI service. Official WhatsApp policies require clear human escalation and only allow normal free-form replies within the 24-hour customer-initiated window.
## Confirmed service enquiries + @Andydotbot owner notifications
A fresh signed WhatsApp service intake creates a random server-only UUID saved in the same FORCE-RLS session. Only after consent, format, user goal and encrypted CRM message are committed, a locked backend finalizer re-checks the current session, owner and non-suppressed CRM thread. It writes one idempotent app.public_service_enquiries row with channel=whatsapp, a fixed non-clinical request summary and private CRM thread as the location for client-written goal, plus an atomic notification_public_enquiry_intents row. /retry_request recovers an interrupted finalizer without creating a second request. STOP shares the same advisory lock and prevents later finalization. A separately gated paired @Andydotbot can dispatch a neutral notification; provider acceptance is not guaranteed delivery. No raw WA phone, client health text or private chat URLs in bot notification.

Migration already applied to existing Supabase: 20261116235946_hh_wa_confirmed_service_enquiry_20261116.sql. It adds service_operation_id and only column-scoped backend SELECT with an operation-scoped FORCE-RLS policy. Never reapply the migration. Real sender/Meta provider E2E remains a release blocker.
