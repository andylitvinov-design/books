# Holistic House CRM — практический план улучшения и приёмки v5

> Продолжение: [Программа развития v5.1 — рабочая очередь, надёжная переписка и следующие этапы](./CRM_DEVELOPMENT_PROGRAM_V5_1_20261020.md). Этот файл сохраняет исходный план релиза v5; текущий статус выпуска проверяется в CRM #985.

**Дата:** 20 октября 2026, America/Toronto. **Источник истины:** `andylitvinov-design/books`, production branch `codex/public-book-library`; [общий Messenger tracking #985](https://github.com/andylitvinov-design/books/issues/985).

## Аудит текущего состояния (до v5)

Реализовано в Production: авторизация через Supabase, владелец CRM с контактами/этапами, consent ledger, business enquiries, кампании только как черновики, email/SMS с собственными ограничениями, омниканальный Messenger-адаптер (ключи провайдеров пока отсутствуют), карточки мастеров, заявки со статусами, группировка только по подтверждённой учетной записи клиента, owner-only legacy archive, внутренняя двусторонняя переписка и заметки, защита клиентской информации, постраничная история, очередь «ждут ответа» и явные отметки просмотра. Клинические документы принадлежат своим отдельным кабинетам и не копируются в маркетинговую CRM.

**Пробелы:** у мастера не было собственных привязанных к заявке задач и сроков; Web Push уже уведомлял согласившегося клиента об ответе мастера, но не наоборот; мастер не мог открыть нужного клиента прямо из push.

## Релиз v5: сделать без дополнительных аккаунтов и расходов

| Приоритет | Функция | Критерии |
|---|---|---|
| P0 | Задачи и follow-up мастера | В заявке: ручные задачи reply/call/booking/check-in/general; дата Toronto, создание, перенос, выполнение, повторное открытие, статус и revision; дубли не создаются после сетевого сбоя |
| P0 | Ограничение данных | Новая таблица FORCE RLS, SELECT/INSERT/UPDATE только для подтверждённого назначенного мастера; клиент, аноним и другой мастер не видят задачи, нет содержания медицинских записей |
| P0 | Уведомления мастеру о сообщении клиента | Только по `message_alerts=true` и `enabled=true` для принадлежащего мастеру Web Push; назначение получателя извлекается сервером из фактической заявки; никакого имени клиента/текста в push |
| P1 | Рабочая очередь | В списке «Мои клиенты»: открытые задачи, просроченные, краткая очередь ближайших действий и фильтр «С задачами» |
| P1 | Навигация | Нажатие на безопасный push открывает `My Practice → Клиенты` и правильную заявку после обычной проверки авторизации и принадлежности |
| P1 | QA и релиз | SQL EXPLAIN, FORCE RLS, пользовательские исходные тесты, GitHub CRM workflow, Vercel READY по точному SHA, проверка ошибок runtime, подтверждение отсутствия новых расходов |

**Правило безопасности:** ни один процесс не отправляет сообщения автоматически в Telegram/WhatsApp/SMS/email. Web Push уже присутствует на сайте, но отправка сообщения мастеру разрешается только после явного согласия мастера в Settings → Notifications. Информация на экране блокировки всегда нейтральна. Отправка не гарантируется: браузер/телефон может блокировать Web Push.

## Следующие фазы, не притворяться «готовыми»

**v6 — многопользовательская CRM:** если мастер захочет делегировать ассистенту, нужны отдельные роли, точечные права к заявкам, отзыв доступа, аудит просмотра и UI назначения ответственного. Никакого доступа по общему флагу «мастер» ко всем клиентам.

**v7 — подтверждение внешних каналов:** владелец отдельно создаёт/авторизует Telegram BotFather и официальные Meta Business/WhatsApp/Instagram/Facebook аккаунты. Только после ключей и разрешений можно выполнить официальный webhook → inbox → ручной ответ → provider receipt. Пока ключей `HH_CRM_MSG_*` нет, real-world delivery OFF. Paid Meta templates, автоматические рассылки и любые клинические рекомендации по сообщениям не включать.

**v8 — реальное E2E и retention:** два авторизованных тестовых пользователя (клиент и именно назначенный мастер) и один чужой мастер; клиентская заявка → shared reply → master alert opt-in → viewed → no leakage → follow-up. Тестовые учётные записи должны быть подтверждены владельцем; нельзя выдавать синтетический PostgreSQL тест за реальную доставку. ## Что сделать владельцу, когда код Live

Откройте [My Practice](https://holistichouse.vercel.app/ru/app/practice) → «Клиенты». Выберите карточку → «Следующие действия». При необходимости настройте в своём кабинете «Настройки → Уведомления на телефон → Уведомлять о новых личных сообщениях», дав разрешение браузеру. iPhone требует добавить сайт на домашний экран через Safari перед Web Push. Никаких BotFather/Meta токенов для этой фазы не требуется.

**Контроль релиза:** отмечать выполненным только код с проверенным live SHA, базу с проверенной миграцией и тесты с фактическим результатом. Если другой коммит публикуется параллельно, проверять, что в новом live SHA сохранены эти функции.
