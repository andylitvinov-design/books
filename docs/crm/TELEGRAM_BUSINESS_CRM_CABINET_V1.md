# Telegram Business → CRM contact → consented Cabinet v1
Owner-approved: reuse existing @holistichouse_bot, human @holistichouse Business chat, CRM and Supabase Auth, without a paid provider, second bot or new account database.

## Flow
1. Customer sends an allowed [HH-REQ] draft from Services, chooses online/in-person/written, types Confirm. A signed, provider-verified business_message plus fresh consent creates one encrypted app.public_service_enquiries, one CRM contact (or reuses the verified prior sender's contact), and one app_private.public_enquiry_contact_links record in the same transaction. Pending, Cancel, STOP and malformed web/browser requests create no lead.
2. Server stores only peer HMACs, not Telegram sender ID, name, phone, message, symptom or diagnosis. No fake phone/email or subscription; CRM source is website due the existing source enum, with encrypted Telegram provenance and a verified Business evidence link. Reply remains in @holistichouse, not falsely mirrored as a bot CRM thread.
3. Existing merged Telegram custom:telegram OIDC + PKCE uses Supabase Auth and ensures app.accounts after verified login. Bot chat is NOT website login. Existing Google users explicitly link Telegram from authenticated Cabinet Settings, without silently merging two user accounts.
4. Once signed in with a verified Telegram OIDC identity, the customer explicitly taps Connect Telegram requests under Cabinet → Settings → Sign-in methods. The server reads only getUserIdentities() and verified numeric OIDC subject, hashes it with the same scope as the signed webhook, and links only a confirmed, not-already-linked Business session. An already linked identity cannot be seized by another account. A separate Disconnect requests revokes the association.
5. The Cabinet shows only own confirmed service title, HH reference, locale/status/date and no private chat or personal data. The original CRM contact/enquiry remain intact after unlink. The owner CRM sees a stable contact for repeated enquiries. Distinct bot-only diagnostic and Business conversations are not misrepresented as one two-way CRM thread.
6. RLS/FORCE RLS on original private tables remains. Added policies are server-role-only (hh_app_backend), proof/operation scoped, with no anon/authenticated Data API grants or SECURITY DEFINER. One shared advisory lock serializes Confirm, Cancel and STOP; DB transaction atomically finalizes request/contact.
7. Database migration already applied to production Supabase project shervdixkaxurnaecioe at 20261114012134 and exact SQL saved at supabase/migrations/20261114012134_hh_tg_business_crm_cabinet_link_v1.sql. No production Telegram clients or Auth users were created by migration.
