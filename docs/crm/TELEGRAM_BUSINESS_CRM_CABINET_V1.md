# Telegram → one Cabinet, no extra request-link confirmation

## Intended single-action UX
- Customer can open the existing Holistic House Cabinet from Telegram. A Telegram bot message itself **never** authenticates the website. Official Telegram OIDC signs in to Supabase Auth through the verified PKCE callback.
- Existing createAppRepository.ensureAccount automatically creates/opens the Cabinet for the authenticated UUID. When the browser already has a verified Google session, Telegram entry uses auth.linkIdentity with the existing signed 10-minute proof; after a successful Telegram OAuth the user returns directly to their Cabinet. No second link button. If no Google session is active, the system cannot safely infer which previous Google account belongs to the Telegram peer. A Google login once is required to prove ownership before merging identities.
- After verified custom:telegram OIDC, the server derives the same keyed peer HMAC as the signed Telegram Business provider. It attaches only previously confirmed submitted requests with CRM contact evidence, under existing per-user RLS; it does not create a new Auth user from a chat message or copy private chat text. The same step runs at Auth callback and retries from Cabinet Settings by same-origin authenticated POST. Settings shows HH references without the separate Connect requests button.
- Disconnect creates a private durable account-scoped opt-out and clears all attached Business sessions in one transaction under a shared advisory lock. Future logins must respect the opt-out; Resume linking is an explicit later opt-in. Do not silently undo STOP or marketing opt-outs.
- Bot-only V3 CRM threads are distinct from signed Telegram Business sessions. Do not auto merge those channels without separate verified peer proof and scoped RLS.

## OIDC identity proof correction (16 November)
Telegram's official OIDC ID token has **two different identifiers**: opaque `sub` and numeric profile `id`. Only the provider-verified `identity_data.id` matches the signed Bot API `business_message.from.id`. The Cabinet helper must never HMAC the OIDC `sub` as a Business peer ID (Telegram's documented sample uses different values). Missing `id` fails closed; no guess from username, phone, email, Supabase user_metadata or sub. Validate the actual Supabase getUserIdentities() shape with two consenting Telegram accounts before switching LIVE flags. Reference: https://core.telegram.org/bots/telegram-login
