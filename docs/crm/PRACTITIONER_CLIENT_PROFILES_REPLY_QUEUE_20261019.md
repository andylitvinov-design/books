# My Practice CRM — профили клиентов и очередь ответов

**Дата:** 19 октября 2026, Toronto. **Источник:** `andylitvinov-design/books` → `codex/public-book-library`.

## Что у мастера уже есть

- `My Practice → Клиенты`: отдельно сохранённые вручную клиенты владельца (админ-архив), заявки на свои услуги и проверенные по идентичности профили запросов. Группировка по серверному HMAC аккаунта и ID мастера, **никогда по совпадению имени, email или телефона**.
- Для каждого профиля: сведения, которые человек указал мастеру, список его обращений и статусов, количество записей в переписке, история сообщений по каждой заявке, рабочие заметки мастера. Внутренние заметки невидимы клиенту; личные тесты, отчёты и обращения к другим мастерам недоступны.
- Прямая двусторонняя переписка внутри Holistic House с клиентом, который вошёл в свой аккаунт. Она не подменяет Telegram/WhatsApp/email и **не выполняет внешнюю доставку**. Заявки через публичную форму без аккаунта поддерживают отдельный ответ по указанному контакту, а не фальшивую «переписку».
- Клиент видит историю своей заявки и ответов в кабинете → Consultations. Каждая операция проходит через подтверждённую сессию, проверки ID запроса, владельца и RLS.

## Доработка очереди ответов

1. Владелец получает фильтр **«Ждут моего ответа»**. Это не «непрочитанные»: сигнал вычисляется по последнему *доступному клиенту* сообщению `visibility='participants'`:
   - новое обращение `requested` без ответа мастера → нужно ответить;
   - последнее видимое сообщение написал клиент → нужно ответить;
   - последний видимый ответ написал мастер → ответ не требуется;
   - заметка `practitioner_note` не считается ответом и не меняет очередь;
   - закрытые заявки и аннулированные запросы не считаются ожидающими ответа.
2. Список клиентов сортируется по **последнему взаимодействию**. Поэтому ответ на старую заявку поднимает клиента выше нового обращения, но частная заметка не «обновляет» его искусственно.
3. Для обновления есть ручная кнопка **«Обновить клиентов»**; нет постоянных запросов, платных уведомлений, скрытой автоматической отправки или передачи клиентского текста во внешнюю аналитику.
4. После отправки сообщения через кабинет мастера список обновляется по действию пользователя. Вкладка клиента и серверный API остаются отдельными, с независимыми проверками.

## Проверка и ограничения

- Запрос последнего сообщения ограничен только собственными UUID заявок конкретного мастера; `DISTINCT ON (request_id)`, индекс `practitioner_request_messages_history_idx`. Выполнен read-only SQL `EXPLAIN` в Supabase — индекс используется.
- На `app.practitioner_request_messages` включён `FORCE ROW LEVEL SECURITY`. Прямого `SELECT` у `anon` и `authenticated` нет. Доступ сервера — только через проверенного участника.
- Ни одна роль мастера не предоставляет доступ к кабинету другого клиента; приватные clinical docs остаются за пределами CRM.
- Данные о настоящей переписке не используются для «тестовых сообщений» и не изменяются данным релизом; никаких новых миграций или провайдерских отправок.
- История доступна только если стороны фактически переписывались на платформе. Утверждения «сообщение доставлено через Telegram/WhatsApp» требуют отдельного официального E2E и остаются запрещёнными до подключения провайдера.

## Приёмка

- Тест с запросом от 1 октября и последним ответом клиента 19 октября ставит его выше клиента с новой заявкой от 18 октября.
- Внутренняя заметка не изменяет очередь ответов; публичная заявка без аккаунта не создаёт скрытую переписку.
- Source tests `tests/practitioner-client-crm.test.mjs` проверяют групповую сортировку, owner-scoped выбор последнего сообщения, интерфейс ручного обновления и сохранение из контекстного чата.
- После GitHub CRM checks нужен Production Vercel build `READY`, проверка live alias/точного SHA и отсутствие регрессий в кабинетах клиента и мастера.
