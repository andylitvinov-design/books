# Holistic House — двусторонняя связь Telegram / WhatsApp ↔ мессенджер мастера

**Дата:** 31 октября 2026. **Репозиторий:** `andylitvinov-design/books`.
**Поставка:** P0 отображение уже доступного диалога в «Переписке»; дальнейшая транспортная интеграция — ОТДЕЛЬНЫЕ проверяемые этапы. **Не утверждать, что физический Telegram/WhatsApp E2E работает, пока он не проверен.**

## Решение для клиента и мастера
1. На странице **опубликованной услуги конкретного мастера** клиент выбирает «Написать в Telegram» или «Написать в WhatsApp». Действие открывает **официального бота / бизнес-аккаунт Holistic House**, не личный аккаунт мастера. Клиент сам отправляет сообщение, прочитывает информацию о конфиденциальности и явно подтверждает согласие на сервисный ответ. Открытие приложения, клик и подготовленный текст сами по себе НЕ являются заявкой или доставленным сообщением.
2. Сервер распознаёт `service_offering_id` и назначенного `recipient_practitioner_id` по одобренному опубликованному офферу. Ссылки могут нести только короткий подписанный, ограниченный по времени state без телефона, Telegram chat_id, здоровья, вопроса, e-mail; подпись и срок проверяются сервером. **Не сопоставлять аккаунты по имени, `@username`, введённому телефону или номеру WhatsApp**.
3. Официальный webhook проверяет подпись / Telegram secret, ограничения на источник, уникальность update/message ID, согласие и `STOP`. До явного согласия не создаёт полноценный lead. Каждое событие сохраняется один раз в существующей зашифрованной CRM; привязка к услуге и мастеру транзакционна. Одна заявка — одна история разговора.
4. В `/{locale}/app/messages` мастер видит **одну карточку**: псевдоним, Telegram/WhatsApp, конкретную услугу, источник `source_path`, номер заявки, статус ответа, время, историю. «Заявки» — стадия обработки, «Переписка» — тот же разговор. Переход не клонирует CRM контакт / сообщения.
5. Мастер пишет только в нашем существующем композере. Backend авторизует **именно назначенного активного мастера для конкретной услуги**, проверяет свежую подтверждённую связь с провайдером, opt-in/STOP/архив/блокировку, допустимое окно ответа, ограничения и уникальный operation UUID. Тело ответа сохраняется только в защищённом серверном хранилище и отправляется через официальный Bot API или Meta WhatsApp Business Cloud API.
6. Клиент получает сообщение **в том же Telegram / WhatsApp**, где начал диалог; его ответ через проверенный webhook возвращается **в ту же беседу мастера**. Статусы `saved`, `queued`, `provider_accepted`, `delivered`, `read`, `failed`, `unknown` различаются; нельзя изображать `delivered` после HTTP 200 от сервера. У Telegram Bot API нет подтверждения реального прочтения. Не делать неоднозначные авто-повторы отправок.

## Что реально есть и что нельзя путать
- Реальный owner-only внешний CRM: `app.crm_msg_accounts`, `app.crm_msg_threads`, `app.crm_msg_items`, `/api/app/crm/messenger`, webhook `/api/app/crm/messenger/webhook/[provider]`, `CrmMessengerPanel`. **Доступ владельца CRM ≠ доступ любого мастера.** Не раскрывать чужие диалоги через владельческий `withOwner`. Использовать новый строго scoped recipient bridge только после независимой RLS/SQL проверки, без выдачи всем мастерам прав owner CRM.
- Реальный защищённый account↔master чат заявок: `app.consultation_requests` и `app.practitioner_request_messages`, `PracticeRequestConversation`, `/api/app/practitioner-client-messages`. Публичная гостевая заявка `app.public_service_enquiries` — **другая сущность**, не имеет автоматического verified account / Telegram identity, её нельзя выдавать за готовый двусторонний чат.
- P0 этого PR: `lib/app/messages-inbox-tabs.mjs` показывает одни и те же уже существующие CRM-лиды в «Заявках» и «Переписке»; account-bound request — в обоих разделах; публичные без внешней verified связи остаются только в «Заявках». Прежние RLS, API, хранилище и отправка не меняются; если канал не готов, композер показывает настоящую причину и не притворяется отправленным.

## Критерии приёмки до объявления LIVE
- Два разных тестовых клиента, два разных мастера; каждый мастер видит только свои заявки, не может открыть чужие через подмену ID.
- Путь `страница услуги → Telegram / WhatsApp реальное сообщение → signed webhook → зашифрованная карточка в существующем Messages → ответ мастера → сообщение в мессенджере клиента → клиентский ответ → та же история` — физическое двустороннее E2E на реальном телефоне для каждого канала.
- Отдельные negative tests: иной chat identity, неверный webhook secret/HMAC, replay/дубликат, STOP, без согласия, после закрытия reply window, закрытая/архивная заявка, анонимная заявка без подтверждённого канала, cross-master IDOR, отсутствие провайдера.
- Нет PII, номеров, token или clinical data в внешних ссылках/логах/статусах; шифрование, FORCE RLS для нужных таблиц; verified linkage и отдельный opt-in. No automatic broadcast.
- Точный PR HEAD: контрактные тесты и relevant CI/security/RLS, независимая проверка, `release-ready`; затем GitHub auto-merge и Vercel READY на exact production SHA + физический E2E. Никакое «готово в коде» не означает «работает на LIVE».
